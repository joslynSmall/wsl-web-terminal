# 业务流程图谱

> 由 flow-closure 维护。**业务需求 / 业务缺陷触发时，先自主研究（优先 `semble` MCP）建立关联关系；研究齐备后把关联关系、待确认问题、证据位置、模型建议交给 `grill-with-docs`，确认结果只回写本目录；`CONTEXT.md` 只维护术语。**
> **先读本页，用"关键词 / 入口"定位业务域，再进入域目录，最后才读具体流程。不要一次读完整个目录。**
> 校验：`node <skill>/scripts/flowmap.js check`　定位：`... locate <关键词>`　影响面：`... impact <流程ID>`　未完成项：`... outstanding`

## 维护规则

1. 本目录是流程事实的唯一权威：业务需求 / 业务缺陷每次迭代必须把代码、测试和对应流程文件同批同步。
2. 流程 ID（2–8 位大写字母或数字）全项目唯一，同时是分支 ID 的前缀：`<流程ID>-B01`，ID 一经分配不复用。
3. 首次建图谱先一次性确认粗粒度业务域划分和命名：有分歧交 `grill-with-docs`；事实依据充分且方案唯一时由模型写出依据直接确认。新业务按决策归属确认后，先在本页登记业务域，再在域 README 登记流程，最后写流程文件。
4. 分支状态：`planned` 需求已定义代码未做 ｜ `wip` 实现中 ｜ `done` 已实现且有测试 ｜ `inferred` 从代码反推待按决策归属确认 ｜ `pending-decision` 仍有分歧 / 未知，待访谈确认 ｜ `removed` 已移除（保留不删）。
5. 做完的标准：访谈完成（待确认问题清空、方案无未决业务选择、每条业务行为落到流程 / 分支并写出终态与不变量），代码 / 测试 / 图谱同批同步，`check` 无错误，涉及的流程 `stamp` 成功且 `drift` 为 `fresh`，且没有遗留的 `planned / wip / inferred`（`pending-decision` 要写明挂起原因）。
6. **流程事实只依据本目录与代码**：已确认的需求文档可作业务语义依据；其他 md 说明只当线索，冲突整理成待确认问题并登记为陈旧文档，需求调研清楚后再处理。
7. 决策归属：有分歧或未知才问用户；模型直接确认须有代码 / 测试 / 已确认图谱的事实依据、唯一明确最佳方案及写出的依据。高风险仍先补测试并披露未验证项。
8. 图谱已盖章（`fresh`）的流程直接信任，不必重读代码；`stale / edited / unstamped` 才需要复核。`.flowmap-lock.json` 是生成物，不要手改。
